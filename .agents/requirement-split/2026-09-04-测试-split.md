## 当前理解

- **需求原文**：测试
- **仓库**：Kanban（`@alipay/dtazzicloud`），一个面向编码 agent 的看板/任务管理工具，TypeScript 单体仓库，Node ≥22。
- **现有测试基建（已勘察的仓库证据）**：
  - 测试框架：Vitest（`vitest.config.ts`，`vitest` devDependency `^4.1.0`）。
  - 主仓测试目录：`test/integration`、`test/runtime`、`test/utilities`，并有 `test/README.md`。
  - web-ui 测试：`web-ui/tests/smoke.spec.ts`（Playwright，见 `web-ui/playwright.config.ts` 被 lint 覆盖）。
  - 相关 npm scripts（`package.json`）：
    - `test` → `vitest run`
    - `test:fast` → `vitest run test/runtime test/utilities`
    - `test:integration` → `vitest run test/integration`
    - `test:precommit` → `npm run test:fast`
    - `test:watch` → `vitest`
    - `web:test` → web-ui 端测试
    - `check` → biome check + typecheck + test
  - `packages/**` 被主 vitest 排除，各自有独立 vitest 配置，由 CI 显式运行（见 `vitest.config.ts` 注释与 `.github/workflows`）。
- **当前推断**：需求可能意指以下任一方向，但均无足够证据确认——
  1. 为某个新功能/模块补充测试用例；
  2. 修复现有测试失败 / 提升 CI 稳定性；
  3. 搭建或改进测试基建（如覆盖率、端到端、性能测试）；
  4. 仅是一次流水线联调用的占位需求。

## 待回答的关键问题

按优先级排列，请产品同学依次回答（目标用户、预期结果、成功指标、范围边界）：

1. **【最关键】这次「测试」想达成什么业务/工程结果？**
   - 是为某个具体功能补测试？修复失败的测试？还是改进整体测试体系？
   - （选项示例：①给指定模块补单测 ②修复 CI 中的测试失败 ③提升测试覆盖率/质量门禁 ④纯流水线联调占位）

2. **目标对象是哪个模块/范围？**
   - 主仓 `src/`？`test/runtime`、`test/integration`？`web-ui`？`packages/` 下某个子工作区？还是全仓库？

3. **成功如何衡量？**
   - 例如：`npm run test` 全绿？覆盖率达到某阈值？某个具体 bug 不再复现？CI 不再因测试挂起？

4. **范围内 / 范围外**：是否包含端到端（Playwright）、性能/负载测试，还是仅单元/集成测试？是否允许改动现有测试基建配置？

5. **是否有时间盒或发布约束**（如随某次发版上线、是否接受分阶段补测）？
