## 一、系统概述

### 1.1 背景
团队目前使用文档记录周报，数据分散且难以追踪进度。需开发一个轻量级周报系统，实现员工提交周报、主管审核并查看团队进度统计的完整流程。

### 1.2 目标
- 员工可创建、编辑、提交自己的周报
- 主管可查看团队周报、审核（通过/打回）周报、查看数据统计
- 提升团队周报管理的效率和透明度

---

## 二、核心角色

| 角色 | 职责 |
|------|------|
| 员工 | 创建、编辑、提交自己的周报 |
| 主管 | 查看团队周报、审核周报、查看数据统计 |

## 三、核心需求

### 需求1：周报草稿的创建与保存（自动保存）

#### 业务规则
- 周报状态默认为`DRAFT`（草稿）
- 文本框失去焦点或每隔30秒触发自动保存
- 前端显示"保存中..."状态提示

#### API设计
- **新建周报**
  - `POST /api/reports`
  - Request: `{ "thisWeekWork": "string", "nextWeekPlan": "string", "status": "DRAFT" }`
  - Response: `{ "code": 200, "data": { "id": 101, "updatedAt": "2023-10-25T10:00:00Z" }, "msg": "保存成功" }`

- **更新周报**
  - `PUT /api/reports/{id}`
  - Request/Response 同上

---

### 需求2：提交周报（状态流转与校验）

#### 前端校验
- 工作内容和下周计划不能为空
- 字数需大于10字
- 校验失败时高亮报错
- 提交前弹出二次确认框："确认提交？提交后不可修改"

#### 后端校验
- 检查该员工本周是否已提交过周报（防重）
- 检查状态是否为`DRAFT`（防非法状态跳跃）
- 校验通过后更新状态为`PENDING`（待审核）

#### API设计
- `PUT /api/reports/{id}/submit`
- Request: `{}`
- Success Response: `{ "code": 200, "data": null, "msg": "提交成功" }`
- Failure Response: `{ "code": 400, "data": null, "msg": "您本周已提交过周报" }`

---

### 需求3：主管审核周报（条件查询与操作）

#### 前端交互
- 默认加载状态为`PENDING`的周报列表
- 可通过下拉框筛选不同状态：全部/待审核/已通过/已打回
- 点击"通过"或"打回"按钮
- 打回时需弹出输入框填写打回原因

#### 后端处理
- 根据查询条件分页返回周报列表
- 审核动作处理：
  - 通过：状态更新为`APPROVED`（已通过）
  - 打回：状态更新为`DRAFT`，并记录打回原因

#### API设计
- **查询接口**
  - `GET /api/reports?page=1&size=10&status=PENDING`
  - Response: `{ "code": 200, "data": { "total": 15, "list": [{ "id": 101, "authorName": "张三", "status": "PENDING", ... }] } }`

- **审核接口**
  - `PUT /api/reports/{id}/audit`
  - 通过请求: `{ "action": "APPROVE" }`
  - 打回请求: `{ "action": "REJECT", "rejectReason": "内容太简略" }`

---

### 需求4：团队周报数据统计（聚合计算）

#### 前端展示
- 团队周报提交率（已提交/团队总人数）
- 审核通过率
- 本周提交人数趋势（折线图）
- 无数据时显示空状态占位符

#### 后端处理
- 聚合查询用户表和周报表
- 计算统计数据返回给前端，避免前端拉取全量数据计算

#### API设计
- `GET /api/statistics/weekly?weekDate=2023-10-23`
- Response: `{ "code": 200, "data": { "submitRate": 0.85, "approvalRate": 0.95, "totalMembers": 20, "submittedMembers": 17 } }`

```
   ↑         ↓

```

## 五、技术决策

### 5.1 自动保存策略
- **前端**: 失焦触发 + 30秒定时器
- **后端**: Upsert逻辑（不存在则新建，存在则更新）

### 5.2 防重提交机制
- 后端校验：同一员工同一周只能有一条有效周报
- 状态校验：只有`DRAFT`状态可提交

### 5.3 分页查询
- 默认每页10条
- 支持状态筛选

### 5.4 统计聚合
- 后端聚合计算，前端仅展示
- 避免前端全量数据计算

### 5.5 并发冲突解决（乐观锁 + 状态校验）

#### 冲突场景
- 员工提交周报后，前端仍停留在编辑页触发自动保存
- 主管同时在审核该周报（通过或打回）

#### 解决方案
**乐观锁机制**：
- 数据模型增加 `version` 字段（整数，默认0）
- 每次更新时校验版本号：`UPDATE ... WHERE id=? AND version=?`
- 更新成功时版本号+1

**状态机校验**：
- 自动保存仅允许 `DRAFT` 状态
- 提交时校验状态必须为 `DRAFT`
- 审核时校验状态必须为 `PENDING`

#### API改造
- 所有写操作请求体增加 `version` 字段
- 冲突响应：`{ "code": 409, "msg": "数据已被修改，请刷新后重试" }`

#### 前端处理
- 收到 409 响应后提示用户并刷新页面
- 自动保存前检查当前状态，非 `DRAFT` 时禁用保存

### 5.6 防抖与节流校验（防止重复提交）

#### 场景
员工疯狂点击"提交审核"按钮，导致：
- 后端收到多次重复请求
- 数据库产生脏数据
- 状态异常

#### 解决方案

**前端防抖（Debounce）**：
- 提交按钮点击后立即禁用，显示"提交中..."
- 请求完成前按钮不可再次点击
- 使用 `lodash.debounce` 或自定义 hook，延迟 300ms

**前端节流（Throttle）**：
- 同一操作在 3 秒内只允许发起一次请求
- 使用 `lodash.throttle` 限制请求频率

**后端幂等校验**：
- 提交接口增加幂等键（`idempotentKey`），前端生成唯一标识
- 后端缓存已处理的幂等键（Redis，TTL 5分钟）
- 相同幂等键的请求直接返回缓存结果，不重复执行业务逻辑

#### API改造
- 提交请求头增加：`X-Idempotent-Key: {UUID}`
- 后端校验幂等键是否已处理

#### 前端实现示例
```typescript
// 提交按钮状态管理
const [submitting, setSubmitting] = useState(false);

const handleSubmit = throttle(async () => {
  if (submitting) return;
  setSubmitting(true);
  try {
    await api.submitReport(reportId, { idempotentKey: uuid() });
    toast.success('提交成功');
  } finally {
    setSubmitting(false);
  }
}, 3000);

// 按钮禁用状态
<Button disabled={submitting} onClick={handleSubmit}>
  {submitting ? '提交中...' : '提交审核'}
</Button>
```

### 5.7 越权访问防护

#### 场景
员工A试图通过修改URL中的 `{id}` 来查看或修改员工B的周报：
- 直接访问 `GET /api/reports/101` 查看他人周报
- 恶意修改 `PUT /api/reports/101` 篡改他人周报
- 越权提交 `PUT /api/reports/101/submit` 冒名提交

#### 解决方案

**后端权限校验（核心）**：
- 每个请求从 Token 解析当前用户身份（`currentUserId`）
- 查询周报时校验：`report.authorId == currentUserId`（员工）或主管权限
- 修改/提交时校验：必须为周报所有者
- 审核时校验：必须为主管角色

**角色权限矩阵**：

| 操作 | 周报所有者 | 其他员工 | 主管 |
|------|-----------|---------|------|
| 查看周报详情 | ✅ | ❌ | ✅（团队周报） |
| 编辑周报 | ✅ | ❌ | ❌ |
| 提交周报 | ✅ | ❌ | ❌ |
| 审核周报 | ❌ | ❌ | ✅ |

**API响应**：
- 无权限时返回：`{ "code": 403, "msg": "无权访问该周报" }`
- 前端统一拦截 403 响应，跳转至错误页或提示"无权访问"

**前端路由守卫（辅助）**：
- 编辑页初始化时获取周报详情，校验 `authorId`
- 若不匹配，显示"无权访问"并跳转
- 防止用户在无权限页面停留

#### 实现示例（后端伪代码）
```java
@PutMapping("/api/reports/{id}")
public Result updateReport(@PathVariable Long id, @RequestBody ReportDTO dto, 
                           @AuthUser User currentUser) {
    Report report = reportRepository.findById(id);
    
    // 越权校验
    if (!report.getAuthorId().equals(currentUser.getId())) {
        throw new ForbiddenException("无权访问该周报");
    }
    
    // 状态校验
    if (report.getStatus() != Status.DRAFT) {
        throw new BadRequestException("周报已提交，不可修改");
    }
    
    // 业务逻辑
    reportRepository.update(id, dto);
    return Result.success();
}
```

#### 审计日志
- 记录所有访问失败的操作（用户ID、目标周报ID、时间）
- 用于安全审计和异常行为分析

## 六、异常兜底逻辑

### 6.1 网络异常处理

#### 场景
- 自动保存时网络中断
- 提交周报时请求超时
- 统计数据加载失败

#### 解决方案

**前端降级策略**：
- 自动保存失败时本地缓存（localStorage），标记"待同步"
- 网络恢复后自动重试，最多3次
- 提示用户："网络异常，内容已本地保存，请稍后重试"

**请求超时处理**：
- 设置请求超时时间：保存接口 10s，提交接口 30s
- 超时后显示"请求超时，请检查网络"提示
- 不自动重试提交操作（避免重复提交），由用户手动重试

**断网检测**：
- 使用 `navigator.onLine` 监听网络状态
- 断网时禁用提交按钮，显示"网络已断开"
- 恢复时自动同步本地缓存

#### 本地缓存结构
```typescript
interface LocalCache {
  reportId: number;
  content: { thisWeekWork: string; nextWeekPlan: string };
  savedAt: string;
  syncStatus: 'pending' | 'synced' | 'failed';
  retryCount: number;
}
```

---

### 6.2 数据异常处理

#### 场景
- 周报数据被误删
- 数据库字段为空或格式异常
- 版本号不匹配

#### 解决方案

**数据校验**：
- 后端返回数据前校验必填字段
- 字段为空时返回默认值，而非 null
- 前端对异常数据做容错渲染

**数据恢复**：
- 周报删除采用软删除（增加 `deletedAt` 字段）
- 管理员可在后台恢复误删数据
- 保留 30 天软删除记录

**版本冲突处理**：
- 版本号不匹配时返回 409 响应
- 前端提示"数据已被修改，正在刷新..."
- 自动拉取最新数据，合并本地修改

---

### 6.3 接口异常处理

#### 统一错误码设计

| 错误码 | 说明 | 前端处理 |
|--------|------|----------|
| 400 | 参数校验失败 | 显示具体错误信息 |
| 401 | 未登录/Token失效 | 跳转登录页 |
| 403 | 无权限访问 | 显示"无权访问"，跳转首页 |
| 404 | 资源不存在 | 显示"周报不存在"，跳转列表页 |
| 409 | 数据冲突/版本不匹配 | 提示刷新页面 |
| 429 | 请求过于频繁 | 显示"请稍后再试" |
| 500 | 服务器内部错误 | 显示"系统异常，请稍后重试" |
| 503 | 服务不可用 | 显示"服务维护中，请稍后" |

#### 错误响应格式
```json
{
  "code": 400,
  "msg": "工作内容不能为空",
  "data": null,
  "traceId": "abc123def456"
}
```

---

### 6.4 业务异常处理

#### 场景
- 周报已提交后再次提交
- 审核已通过的周报
- 打回时未填写原因

#### 解决方案

**状态前置校验**：
- 每个操作前校验当前状态是否允许
- 状态不匹配时返回明确错误：`{ "code": 400, "msg": "周报已提交，不可重复提交" }`

**必填项校验**：
- 打回时后端校验 `rejectReason` 不能为空
- 返回：`{ "code": 400, "msg": "打回原因不能为空" }`

**业务规则校验**：
- 同一员工同一周只能有一条周报
- 返回：`{ "code": 400, "msg": "您本周已提交过周报" }`

---

### 6.5 容灾与降级

#### 数据库故障
- 数据库连接池超时（5s）后返回友好错误页
- 使用缓存兜底（Redis）显示只读数据
- 提示："系统维护中，部分功能暂不可用"

#### 服务降级策略
- 统计接口失败时显示"数据加载中..."占位符
- 不阻塞核心功能（周报编辑、提交）
- 列表查询失败时显示空状态，提供"重新加载"按钮

#### 重试策略
- 自动保存失败：指数退避重试（1s、2s、4s），最多3次
- 其他操作：不自动重试，由用户手动触发

---

### 6.6 日志与监控

#### 异常日志记录
- 记录所有异常请求：用户ID、请求路径、错误码、traceId、时间戳
- 使用结构化日志格式（JSON）

#### 前端错误上报
- 使用 Sentry 或自建错误上报服务
- 捕获未处理异常，自动上报
- 包含：错误堆栈、用户环境、操作路径

#### 告警规则
- 接口错误率 > 1%：触发告警
- 单接口 5xx 错误连续 10 次：触发告警
- 响应时间 > 3s 持续 5 分钟：触发告警
