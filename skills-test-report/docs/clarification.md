## 1. 需求理解

### 1.1 核心目标

为 Agent 提供一个「生成测试报告」Skill，在测试执行后（或收到已有结果文件时）自动解析结果，产出**固定结构、可读性强、可沉淀**的标准化测试报告。

一句话指令（如「生成测试报告」）即可完成：执行测试 → 收集结果 → 生成报告（G1）。

### 1.2 价值定位

解决测试结果散落在终端/CI 日志/框架原生产物中的四大痛点：人工收集耗时易遗漏、缺统一格式跨团队沟通成本高、失败用例上下文需人工回溯、质量指标无法沉淀为可追踪历史数据。

### 1.3 现状对齐

经通览 `skills-test-report/` 目录，发现该 Skill **已有初版骨架**：

- `SKILL.md` v1.0.0：内容与需求文档高度对齐（框架范围、双模式、配置项、报告六板块、失败处理、落盘均已映射）。
- `src/`：`config.ts`、`detect.ts`、`models.ts`、`parsers/`（jest-json、junit-xml、pytest-json、pytest-junit、vitest-json、registry）、`report/sections/`、`security/redact.ts`。

**结论**：需求文档并非从零规划，而是对已规划 Skill 的需求澄清与范围确认。本阶段产出澄清结论，供后续编码实现阶段直接引用。

| 工作模式 | 执行模式（检测命令→运行→解析→报告）+ 解析模式（跳过执行，直接解析已有结果文件） | FR1.3 / US4 / AC3 |

| 报告结构 | 报告头→结果摘要→失败用例分析→用例明细→覆盖率→附录（固定顺序） | FR2 / AC1 / AC2 / AC5 |
| 失败诊断 | 测试命令无法运行/结果文件损坏时返回明确诊断，不生成空报告 | FR1.4 / AC4 |
| 落盘 | `reports/test-report-<YYYYMMDD-HHmmss>.md`，返回路径+摘要 | FR3.2 / FR3.3 / US1 |

### 2.2 P1 范围（M2/M3，本期可选）

- M2：pytest 支持（JUnit XML/JSON）、覆盖率章节完善、`fail_threshold` 通过率阈值。
- M3：HTML 输出、JSON 伴随产物。

### 2.3 非目标（明确不做）

- 测试用例自动生成或修复（仅报告）。
- 报告在线托管 / Web 服务化展示。
- 多次运行结果趋势对比分析（后续迭代候选）。
- 非测试类质量报告（lint、安全扫描）聚合。
- 报告自动推送 IM / 邮件（Q3 裁决：否）。

## 3. 开放问题静默裁决

> 依据硬性约束「全流水线模式 / 静默接管所有决策权」，以下开放问题基于仓库现状证据与需求文档内在线索直接裁决，不阻塞流程。

### Q1：首期目标项目栈是否以 TypeScript/Node 为主？

- **裁决：是，以 TypeScript/Node 为主栈。**
- 依据：
  - dtazzi-cline 仓库为 TypeScript 项目（`package.json`、`vitest.config.ts`、`tsconfig.*`）。
  - 现有 `SKILL.md` P0 已含 Jest/Vitest JSON reporter。
  - 需求文档已按此假设制定 P0 范围（见 4.1 注释）。
- 影响：P0 解析器优先实现 jest-json、vitest-json、junit-xml（兜底）。

### Q2：报告是否需要中文/英文双语模板，还是仅中文？

- **裁决：仅中文（P0/M1）。**
- 依据：
  - 需求文档、现有 `SKILL.md`、`AGENTS.md` 均为中文。
  - 双语模板增加复杂度且非核心价值，降低 P0 交付风险。
- 约定：报告正文中文；配置项名称、字段标识符、技术 token（如 `test_command`、`output_format`）保留英文原文，不翻译。

### Q3：是否需要将报告自动推送到 IM / 邮件等渠道？

- **裁决：否，本期不做推送。**
- 依据：需求 2.2 已明确列为非目标；本期聚焦报告生成本身。
- 影响：Skill 输出仅落盘 + 返回 `{ path, summary }`，不集成任何推送通道。

## 4. 隐性澄清点（需求文档未显式列出但需确认）

### C1：现有 src 已含 pytest 解析器，M1 是否裁剪？

- **裁决：不裁剪，插件式共存。**
- 依据：NFR5 要求插件式结构，新增框架不影响既有解析器。pytest 解析器代码已存在，M1 不主动暴露但保留，M2 激活即可，零额外成本。
- 影响：`parsers/registry.ts` 注册顺序按 P0 优先，pytest 解析器标记为 P1 可用。

### C2：覆盖率「低于阈值的文件清单」的阈值默认值？

- **裁决：默认 80%（语句覆盖率），可通过配置项覆盖。**
- 依据：需求 FR2 第 5 点要求「低于阈值的文件清单」但未给默认值；80% 为行业惯例合理默认。
- 影响：新增隐性配置项 `coverage_threshold`（默认 0.8），覆盖率章节据此筛选文件。

### C3：执行模式长任务如何处理（R2 风险）？

- **裁决：委托运行时后台任务（`run_in_background=true`），轮询收集结果，不阻塞 agent turn。**
- 依据：现有 `SKILL.md` 已声明此策略；符合硬性约束全流水线不阻塞。
- 影响：执行模式实现时，测试命令通过后台任务运行，解析与报告生成在前台完成。

### C4：报告模板语言与时间戳格式

- **裁决：中文模板；时间戳格式 `YYYY-MM-DD HH:mm:ss`（本地时区）；文件名时间戳 `YYYYMMDD-HHmmss`。**
- 依据：需求 FR3.2 已规定文件名格式；报告头生成时间取本地可读格式。

### C5：幂等性（NFR4）的「时间戳字段除外」具体范围

- **裁决：仅「报告头-生成时间」与「文件名时间戳」为非幂等字段；其余报告体（摘要数据、失败分析、明细、覆盖率、附录）对同一结果文件多次渲染须字节一致。**
- 依据：NFR4 要求内容一致（时间戳除外）；明确边界避免实现歧义。

## 5. 报告结构（固定顺序，确认稿）

> 与需求 FR2 / 现有 SKILL.md 完全一致，此处确认最终结构。

1. **报告头**：项目名、生成时间、执行命令、框架/版本、执行环境摘要（已脱敏）。
2. **结果摘要**：用例总数、通过/失败/跳过数、通过率、总耗时；整体结论 ✅/❌（低于 `fail_threshold` 时附「不达标」）。
3. **失败用例分析**（有失败时必选）：每条含用例名、所属文件、错误信息、堆栈关键行（截断至可读长度 + 脱敏）。
4. **用例明细**：按测试文件分组；超过 200 条时截断并注明「已截断，共 N 条」。
5. **覆盖率**（可获取时）：语句/分支/函数/行覆盖率总表 + 低于阈值（默认 80%）文件清单；缺失时标注「未获取」。
6. **附录**：原始结果文件路径、生成工具版本。

## 9. 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| R1：各框架 reporter 输出差异大 | 插件式解析器结构（NFR5），每框架独立解析器，registry 统一调度 |
| R2：测试执行耗时不可控 | 委托运行时后台任务（`run_in_background=true`），轮询收集（C3 裁决） |
| R3：结果文件格式异常/字段缺失 | 降级输出「未获取」，不崩溃不静默丢数据（NFR2） |
| R4：报告泄露敏感信息 | `security/redact.ts` 脱敏堆栈中凭据路径，报告不含环境变量/密钥（NFR3） |
| R5：幂等性实现歧义 | 仅时间戳字段非幂等，其余报告体字节一致（C5 裁决明确边界） |
